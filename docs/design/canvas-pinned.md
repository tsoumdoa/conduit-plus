# Pinned canvas cards — design, 2026-11-18

Status: accepted by the owner 2026-11-18; see Owner decisions. A HUD inside the GH canvas client area, fixed in screen size while the definition pans and zooms underneath. A floating window is deferred.

## Component shape

Add **Canvas Overlay** under Display: **Cards** (tree, collected once in tree order), optional **Theme**, optional **Scope**; **Selection** output. Theme input/menu precedence and Auto resolution match Overlay. Slot comes from each card, not a second layout input. No Links, View, Size or Events input/output in this first version. The ordinary component capsule remains in the definition for wiring, warnings and finding the display's owner; its location has no effect on the HUD.

Use Overlay's valid-sibling validation and duplicate diagnostics; no inherited 12-card stack limit. Fit and memory limits report omitted cards. One component can supply a dashboard. Several components in the same document share one layout, but retain separate themes, local view state and private selection unless explicitly scoped. Allocate one new stable GUID; change no existing GUIDs or input positions. Future inputs append with `AppendedInputs.Read` compatibility handling.

Rejected: **Pin to window** on Canvas Card makes one component alternate between a measured GH body and a window-owned dashboard, changes Slot meaning by mode, and complicates export, saved bounds and duplicate presentation. Existing Canvas Card remains useful beside its producers. Users can connect the same cards to either or both displays. A new component makes the target explicit, as Overlay does for Rhino.

## Verified API and host choice

Metadata reflection on `~/.nuget/packages/grasshopper/8.20.25147.11001-rc/lib/net7.0/Grasshopper.dll` reports assembly `8.20.25147.11001`. Its XML marks the widget types `<exclude/>`.

- Public abstract `GH_Widget` exposes `Owner: GH_Canvas`, read/write `Visible`, `Render(GH_Canvas)`, `Contains(Point control, PointF canvas)`, mouse down/move/up/double-click and key down/up responses, tooltip region/setup, and `AppendToMenu`. Responses return `GH_ObjectResponse`. There is **no widget wheel override**.
- Public abstract `GH_CanvasWidget_FixedObject` adds virtual `ControlLocation(GH_Viewport)` and `CanvasLocation(GH_Viewport)`, abstract read/write `Ratio: SizeF`, read-only `Size: Size` and `Padding: int`, and protected abstract `Render_Internal` with control/canvas locations and bounds. It describes one anchored object, not a multi-slot dashboard.
- `GH_Canvas.Widgets` returns `List<IGH_Widget>`; `GH_CanvasWidgetListEventArgs.AddWidget(IGH_Widget)` is public. `WidgetListCreated` is **static**, raised inside canvas construction, before an instance handler could attach. `Instances.CanvasCreated`, `GH_Canvas.Canvases`, `ActiveWidget`, `DrawingMode`, and pre/post widget and post-overlay paint events are available.
- Correction to the initial finding: **Compass** derives from FixedObject; **Profiler and Markov derive directly from GH_Widget**. Neither provides public widget bounds. Markov exposes public dock corner/icon limit settings and change events; its area properties are private.

Choose **one registered GH_Widget per canvas**, with a per-active-document coordinator behind it. Derive directly from GH_Widget and let the shared layout supply rectangles. Use GH's widget dispatch, capture and tooltip integration. Reject paint events plus independent mouse routing: drawing alone supplies no input precedence, and a second router would have to reproduce GH interaction cancellation and menu behavior. Do not also paint in `CanvasPostPaintOverlay` or `CanvasPostPaintWidgets`.

Signatures are verified; dispatch order, Graphics transform, tooltip coordinates, menu discovery and export invocation are **live gates**, not established by reflection. Keep the excluded API in a small, lazily loaded GH widget adapter assembly; the component/presenter must not expose widget types in their signatures. Catch adapter load/registration failures at that boundary, leave existing displays usable, and show one persistent component error. After a render/input failure, release owned capture, withdraw the HUD and its hit regions, dispose its resources and report the fault once. No invisible blocker or automatic paint-event fallback. Test pinned 8.20 and the installed newer Rhino; repeat the adapter checks on supported host upgrades.

## Registration and lifetime

Start the host service from plugin loading, not component constructors. Subscribe to static `WidgetListCreated` before future canvases are constructed; add through the event arguments. Also reconcile canvases with existing handles through `GH_Canvas.Canvases`/ActiveCanvas, adding to `Widgets` only when absent and assigning `Owner`. `CanvasCreated` attaches instance lifecycle hooks and reconciles idempotently; it cannot replace the earlier widget-list hook. Never modify a widget list while GH is enumerating it for paint/input.

Retain exactly one widget per canvas, including when it currently has no displays. The widget reads only publications whose document is reference-equal to `canvas.Document`; never infer the document from the current Rhino viewport. On `DocumentChanged`/unload, cancel gestures, clear origin-owned hover/tooltips, remove screen frames and pending work, and retain managed cards, sort, scroll and selection for return without a solve. Close/delete removes publications and Scope leases; canvas disposal removes hooks, widget references, images and timers. Static service shutdown unsubscribes its hooks. Guard queued work by canvas, document, owner and generation.

Per-component **Preview off / Hidden** and **Enabled off / Locked** hide the display's cards entirely, for both Canvas Overlay and viewport Overlay. No bitmap, hit region, tooltip or originating hover remains; cancel active gestures and release capture. Remove hidden owners from layout participation so the remaining cards reclaim their space. Viewport Overlay also withdraws linked-geometry highlight wires and excludes its cards from ConduitPlusCapture/Pdf. Keep authored cards, sort/scroll, selection and Scope leases: presentation visibility never prunes membership. Hidden but enabled participants keep receiving Scope selection and Selection output refreshes; Locked retains `SetEnabled(false)` and frozen membership until GH's normal re-enable solve.

Preview changes only redraw the appropriate host (GH canvas or Rhino views), never solve. Use standard GH Preview menus, Hide/Show Selected and shortcuts, native persistence/shading and native undo/redo. Pinned 8.20 metadata reflection shows `GH_Component.Hidden` is non-overridable (its interface accessors are final virtual), backed by a field and emits no event; `IsPreviewCapable` is virtual and otherwise scans parameters. Override the latter to true for both displays. `GH_ActiveObject` archives Hidden and defaults it to false when absent. Native menu/bulk commands emit `ObjectChanged(Preview)`, but `GH_HiddenAction` undo/redo sets the preview interface without that notification. A small shared component base reimplements `IGH_PreviewObject.Hidden` using GH's original storage and emits the missing Preview event, including on native undo/redo. Enabled changes already emit the native event from Locked's setter. Component GUIDs and parameter order remain unchanged.

Disabled documents still retain their last complete frame with no card actions and frozen membership, but there is no **Disabled** chrome. Unlock reprojects the latest domain snapshot. Pausing the global solver retains the last results and allows local sort/scroll and selection repaint; Selection output remains pending until GH can solve again. Distinguish global solver pause from `document.Enabled == false`; never force-enable either. GH's document-wide preview mode (off / selected only) intentionally does not control these displays: per-component Hidden/Locked and the separate widget toggle determine visibility. Canvas Card's component-body behavior is unchanged. Deletion removes cards immediately, even with the solver paused.

Expose one **Conduit+ cards** entry in GH's Widgets menu through `Visible`/`AppendToMenu`, plus a **Show pinned cards** recovery action on Canvas Overlay. Hiding withdraws all hits/capture and hover, but keeps publications, membership and selection. This global widget toggle combines with each component's Hidden/Locked state; the recovery action enables the widget but does not override the component's Preview or Enabled flag. Menu visibility is a canvas-session preference, not selection state or a reason to solve. Test both hide and rediscovery: presence in `Widgets` alone does not prove the menu works.

## Rendering and cache

Use `RasterDrawing.Render → GdiCanvas → CardPainter`, with GH-owned Bitmaps; no DisplayBitmap or Rhino conduit. A shared presenter owns immutable authored specs, projected state, CardStore revisions, frames and raster leases. Canvas Card attributes and the pinned widget are adapters; a later floating window can use the presenter/controller with its own client rectangle and DPI.

One design unit is one device-independent screen pixel. Raster scale is **device DPI / 96 only**, derived from the actual canvas control/target once. Save/restore Graphics, establish control-pixel coordinates in the adapter, clip to the client/safe area and composite at integer device origins. Never use `Viewport.Zoom`, canvas translation or the canvas world-to-device scale for the HUD. Pan/zoom therefore causes **zero card rasterizations**. Window resize moves or hides cards without changing their scale; monitor DPI changes regenerate them.

Cache by `(owner, cardId, stored Rev, complete resolved Theme, measured size/form, DPI raster plan)`. Input Rev is not authoritative. Location and canvas zoom are absent. Brush/sort/scroll updates may change revisions; theme changes invalidate even without a spec revision. Publish pixels, projected specs, hit regions and placement generation together. During replacement, use the last complete frame only while its owner/document remains eligible; disable stale actions. On failure retain that frame with a notice, or withdraw it if its geometry is no longer safe. Painting never solves GH.

Generalize `CanvasCardCache` scheduling and accounting so inline and pinned displays share **64 MiB per document**, including old/new frames and temporary allocations. Keep the existing **16 MiB / 4096 pixels per bitmap** ceiling and checked allocation arithmetic. Evict hidden/least-recently-visible rasters first; queue bounded UI-thread work. For pinned cards, do not silently reduce raster density to fit: report an oversized card or memory omission in overflow and keep a useful bounded frame. Avoid perpetual evict/re-render churn. These are raster-byte budgets, not promises about total process memory.

Draw in the normal widget layer above definition objects/wires, below GH tooltips, menus and modal interaction chrome. Existing GH widgets win any residual hit conflict; safe-area planning prevents visual overlap. Verify actual widget draw/hit order together before shipping. No late paint pass that covers tooltips. Dispose owned bitmaps/fonts/brushes; `GdiCanvas` does not own the supplied Graphics.

## Interaction and Scope

Extract a Rhino/GH-free **CardInteractionController** from `CanvasCardAttributes`, used by both adapters. It consumes a published frame, card-local and control-space points, modifiers and lifecycle signals; it returns capture/release, repaint and committed actions. Hosts translate GH events and own physical capture/tooltips. Reuse `CanvasCardState`, `CardMeasure.Hits`, `TableSort`, `TableScroll` (including Bars), keyed group selection/Clear and `Tooltip.For`; do not copy the current handler methods into the widget.

Preserve press/release target identity, the four-control-pixel click threshold, Shift-add/Ctrl-remove/Ctrl+Shift-toggle, scrollbar track/thumb and cancellation with offset rollback. Cancel on Escape, lost capture, navigation, hide, document/data/layout/DPI change and disable. Swallow the release belonging to an accepted gesture even after cancellation. Attributes retain their `ActiveObject` behavior; the widget uses verified `ActiveWidget` capture semantics. Check only capture we own before releasing it. Do not start HUD input during an existing GH wire/drag/modal interaction.

Hit the visible card bodies and HUD controls **before underlying canvas objects**. Inert card padding consumes ordinary left clicks without selecting or dragging an unseen component. Outside their union, including gaps and shadows, return pass-through. Right-click inside opens the HUD/owner menu; middle navigation and Alt gestures pass through, while supported selection modifiers work on keyed targets. Tooltip regions use the same published frame and a host coordinate adapter; hide tooltips during gestures and re-hit after sort/scroll. No remote tooltip from Scope hover.

**Wheel stays GH zoom everywhere**, matching Canvas Card. Users scroll tables/Bars with the scrollbar. The pinned cards remain stationary while the definition zooms underneath; this preserves navigation and needs no undocumented wheel interception. Defer optional modified-wheel scrolling until a consuming canvas handler is verified. Do not install the Rhino global wheel hook.

Bind once per component through `ScopeBroker.ForDocument(...).Attach(..., selectionOutput: true)`. Publish all original valid cards, including hidden/overflow cards, with no Link keys; use solution-end transactions and existing generation/feedback guards. Unwired displays keep private domains. Invalid/multiple/foreign tokens disable brush interaction and report the existing Scope error. Overlay alone owns Links and geometry highlighting: sharing a Scope makes pinned selection reach its linked model without transferring geometry to GH.

Generalize `CanvasCardState` carefully: it currently strips `WiredSlot` and hard-codes `sourceSurface: "canvas"`. Retain authored slot data for layout, keep local sort/scroll separate, and supply `"canvas-pinned"` as the new surface/origin while preserving the old value for Canvas Card. Hidden presentation must not prune shared membership. Selection is the sorted effective member set of the whole domain; user selection/Clear requests the broker's coalesced output refresh, while hover/sort/scroll/hide do not. Keep bounded reconciliation and pending-refresh-on-resume behavior.

## Control-space layout and safe areas

Add pure **PinnedCanvasLayout** over a control-client rectangle, DPI, owner-qualified cards, explicit text measurer and host exclusion rectangles. Reuse `SlotLayout.ResolveAll` (automatic slots group producer iterations) and extract shared packing/overflow helpers from `ViewportLayout`; do not call its proportional-scale policy unchanged. Pinned policy fixes zoom at **1**, disables shrink/automatic compaction, and keeps authored widths/row limits. Titles retain their title-only positions and alignment; use a stable authored-width presentation so window resize does not rewrap/re-raster them. Existing Overlay behavior stays unchanged.

Start with 12 DIP margins, 8 DIP gaps and the viewport layout's 35% central keep-clear area, tunable after live testing. Exclude scrollbar/navigation chrome before packing. Use left `tl/lc/bl` and right `tr/rc/br` rails: top from top, bottom anchored as a block, centre clamped between; input order is top-to-bottom within each stack. Wrap inward before hiding. Preserve side anchors in narrow windows rather than rotating into viewport portrait bands. Across owners, use the existing ordinal InstanceGuid tie-break and `(owner, cardId)` identity; same source in two displays is two placements.

Built-in widget exclusions belong to the GH adapter, not Core. Compass can use its public FixedObject location/size with a safety margin. Markov needs a conservative corner reservation based on public DockCorner/IconLimit plus a footprint measured in the 8.20 live probe; recompute on setting/visibility/DPI changes. Do not reflect its private area properties or guess a fixed bottom-left margin. `Contains` can validate hit conflicts but does not establish a widget's full painted extent.

Profiler is not a fixed-corner widget and has no public bounds contract; its timing labels sit beside components in canvas space. **Owner decision (2026-11-18): coexist.** Pinned cards stay visible while Profiler is on and may cover some labels, exactly as they cover components; panning reveals them. Do not suspend the HUD for Profiler. Unknown third-party widgets cannot have guaranteed painted bounds: yield their hits and document this limit, with hide always available.

When cards still do not fit, reserve a **+N cards** chip, hide last-input cards round-robin across owners, then retry earlier hidden cards as in ViewportLayout. Titles hide last. Chip click opens a bounded list of hidden titles grouped by owner, with a **Find component** action; no overlapping temporary full-card popup in this first version. Report count/reason on each affected component using replaceable notices, without erasing solve diagnostics or expiring a solution. If even the chip cannot fit, draw nothing and leave the notice/menu recovery available. Never shrink text or trap the whole client area to make a dashboard fit.

Offer a session-only **Collapse cards** control, reducing the dashboard to a small restore chip, and full Hide through Widgets/owner menus. Collapse/hide preserve data, sort/scroll and selection and cancel interaction; they do not enter GH undo. An exclusion/resize change immediately withdraws unsafe hits; only a complete layout/frame re-enables them. Geometry signatures exclude pan, canvas zoom, hover and selection.

## Export

An operating-system/window screenshot includes the HUD exactly as seen, including transient UI. **GH definition image export excludes pinned cards**, since tiled definition space has no unique window anchor. The widget returns without drawing or registering hits whenever `DrawingMode != Control`, even if GH invokes widget rendering during export. Existing inline Canvas Cards continue their current export behavior. `ConduitPlusCapture`/Pdf remain viewport commands. A dedicated HUD/dashboard export can reuse presenter snapshots later; do not promise it here.

## Verification and delivery

Pure Core xUnit: `PinnedCanvasLayout` containment, no collisions with exclusions/cards, six slots, source grouping/order, multi-owner identities, fixed size at all window dimensions, zero/tiny clients, oversize cards, overflow/reinsertion and chip fallback; `PinnedHitTransform` control ↔ local round trips at fractional DPI, shadow offsets, clipping and unchanged results across arbitrary canvas pan/zoom; `CardInteractionController` modifiers, target-on-release, cancellation/rollback, release ownership and empty-body/pass-through decisions. Extend cache tests for revision/theme/DPI invalidation, pan/zoom reuse, peak allocation and eviction pressure. Scope tests cover the new surface, hidden membership and bounded output feedback. No RhinoCommon at test runtime; use the existing source-linked GDI pattern for raster checks.

Live Rhino 8.20 and installed-version gates: early/late canvas creation and duplicate registration; Widgets hide/show/recovery; definition pan/continuous zoom with raster counters staying flat; mixed DPI; every card kind; overlapping canvas objects, wire creation and middle/Alt navigation; capture lost outside the window, double-click and Escape; tooltip layering; Compass, all Markov corners/icon counts, Profiler coexistence and scrollbars; small windows and several displays; preview off, lock/disable, global solver pause/resume, tab return without solving, delete/undo and close with queued work; pinned ↔ Overlay ↔ model Scope selection and output feedback; tiled GH export exclusion versus window screenshot inclusion. Check GDI handles/raster bytes plateau and full cleanup after repeated close/reopen. Record dispatch/transform/export findings before accepting the widget adapter.

Small stacked PRs, each reviewed before its dependent cutover:

1. **Shared interaction/presenter seam.** Extract controller and generalize surface/slot handling; existing Canvas Card behavior and frozen-file loading remain the regression baseline. No pinned UI yet.
2. **Widget host and one-card vertical slice.** Adapter loading/registration, control-space DPI rendering, lifetime, menus, safe failure and export exclusion. Gate on the live API checks; no paint-event alternative hidden in this PR.
3. **Dashboard layout and resource accounting.** Shared packing policy, built-in exclusions, fixed-size multi-owner frames, overflow notices/list, collapse and the combined cache budget. No silent overflow interim release.
4. **Selection integration and release checks.** Wire the shared controller, Scope/Selection scheduling and tooltips into the pinned host; verify all lifecycle/feedback cases, examples and README. Earlier slices may be explicitly preview-only, not the completed feature.

The reviewing/committing agent builds/tests and packages each implementation from the combined clean integration checkout under AGENTS.md, using the next unused Yak prerelease. Design work remains uncommitted and needs no package. No public publishing or Rhino restart/termination by this task.
